# JSON contract, version 1

The CLI writes one JSON object to stdout. Except for `--help` and `--version`,
argument, input, layout, and report-budget errors also produce an `invalid` report. Exit codes
are 0 clean, 1 conflict, and 2 invalid. A crash or missing output is never a pass.
JSON object keys are sorted; arrays use deterministic ordering. No timestamp,
absolute input location, or discovered target-environment state is added to
successful reports. Invalid-input exception messages may include input paths.

Top-level fields:

- `schema_version`: integer `1`. Consumers must reject unsupported versions.
- `status`: `clean`, `conflict`, or `invalid`.
- `profile`: `posix-case-sensitive-v1`.
- `layout`: validated explicit layout, or null if unavailable/invalid.
- `wheels`: successfully projected inputs, sorted by normalized distribution.
  Each has `distribution`, `version`, `wheel` (basename), and `archive_sha256`.
  This list may be partial when the report is invalid. A report-byte-limit
  error resets the report to an empty invalid result.
- `claims`: all attempted file writes in the supported installation model,
  sorted by path, distribution, wheel, kind, source, and scheme. Empty if invalid.
- `conflicts`: sorted by path and type. Empty if invalid.
- `errors`: validation/projection errors with `wheel` (basename or null) and
  diagnostic `message`. Diagnostic wording is not a stable machine interface.
- `limits`: fixed input bounds applied by this version. These are not a full
  operating-system memory/CPU sandbox. See [limits](limits.md).

Each claim contains:

- `distribution`, `version`, `wheel`: its owning input identity
- `path`: absolute projected POSIX destination
- `scheme`, `relative_path`: selected installation scheme and path beneath it
- `kind`: `file`, `raw-script`, `generated-console`, `generated-gui`, or `generated-record`
- `source`: archive member name, or generated command's `name = module:attribute`
- `sha256`, `size`: transformed output bytes' digest and length
- `executable`: whether the model requests executable output; not a full mode,
  ACL, umask, or filesystem-permission model

The input archive digest identifies an artifact. Claim digests refer to projected
bytes after script rewriting or generation. They are consistency identifiers,
not signatures or authenticity evidence. A generated RECORD is itself a claim;
additional pip metadata and compiled bytecode are not generated by this model.

`shared-file` conflicts contain `path`, `content` (`identical` or `different`),
`command_overlap`, and `claims`. Identical means all bytes have the same SHA-256
and length. It does not claim identical permissions or safe shared ownership.
`command_overlap` is true when at least one claimant is a generated console/GUI
command. Raw-script/raw-script collisions are ordinary shared-file conflicts.

`file-directory` conflicts contain `path`, `file_claims`, and
`descendant_claims`. A file blocks a directory needed by those descendants.
Shared directories without a blocking file produce no conflict.

Even multiple writes from the same wheel are conflicts. Multiple artifacts for
the same normalized distribution instead invalidate the input set. Wheel order
never selects a winner. Consumers must not ignore `invalid`, infer completeness
from a partial `wheels` array, or treat identical-content conflicts as clean.
